<objective>
Make the memory-bank call-record and index schema carry the additive Drive fields, and LOCK the
file-ID dedup rule, before Phase 4's ingest writes the first Drive-sourced call. This phase is
purely additive edits to one file — `gtm-coach-pro/references/memory-bank.md` — with zero structural
change to the existing schema, so an API-sourced call is unaffected.

Purpose: Phase 2 (`drive-source.md`) already named the fields the parse output must carry
(`notes_doc_id`, `transcript_doc_id`, `drive_folder_id`, `source: google-drive`) and deferred wiring
them into storage to "Phase 3." This is that wiring. The load-bearing decision is the dedup key: the
notes-doc Drive file id, never a synthesized title+date — locked here so every call Phase 4 writes
inherits the correct identity from day one.

Output: `gtm-coach-pro/references/memory-bank.md` with (1) additive optional Drive fields in the call
frontmatter template and the `index.json.calls[]` schema, and (2) an extended `## Dedup rule` that
explicitly covers file-ID sources.

Artifacts this phase produces (new schema fields, all optional, present only when `source: google-drive`):
- `source: google-drive` — the discriminator value that gates the fields below
- `notes_doc_id` — the notes-doc Drive file id; == the call id for a Drive-sourced call
- `transcript_doc_id` — the paired transcript Drive file id, or null; never the call/dedup id
- `drive_folder_id` — the parent folder id at time of ingest
- Dedup-rule lock — Drive calls dedup on `notes_doc_id`, never title+date; re-ingest on `modifiedTime`/content-hash change updates the same record

Requirements: SCHEMA-01 (additive optional fields, no structural change), SCHEMA-02 (dedup keys on the
notes-doc file id, re-ingest on edit without a duplicate).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted Drive Doc metadata (title, `createdTime`) → the call's dedup identity | An attacker-influenceable or accidentally-colliding title+date could merge or duplicate distinct calls if the dedup key were derived from it instead of the immutable file id |
| An edited notes doc (changed `modifiedTime`) → an existing call record | A re-ingest must update the existing record, not spawn a duplicate that silently forks a deal's call history |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Spoofing | dedup identity (Task 1) | medium | mitigate | Key the Drive call on the immutable notes-doc Drive file id (`notes_doc_id`), never a synthesized title+date — removes the attacker/collision-controllable identity surface; the title+date fallback is documented as applying only to sources with no stable id |
| T-03-02 | Tampering | re-ingest on edit (Task 1) | low | mitigate | A changed `modifiedTime`/content hash re-ingests into the SAME call record (update in place, bump `updated_at`), never a second call file — an edit cannot fork call history |
| T-03-03 | Tampering | schema surface (Task 2) | low | mitigate | Drive fields are strictly additive and optional, gated on `source: google-drive`, with no structural change to the existing schema — an API-sourced record's shape and dedup behavior are provably unaffected (positive-grep preservation checks) |
| T-03-SC | Tampering | package installs | n/a | accept | No npm/pip/cargo installs — markdown-only edits to one reference doc; Package Legitimacy Gate N/A |
